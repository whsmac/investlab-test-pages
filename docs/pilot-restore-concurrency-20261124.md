# Concurrent restore — isolated PostgreSQL integration
This is an independent two-connection fixture test, not a production migration or device/browser test. PR #24 domain and rollback checks succeeded (run 45385244920).
The test creates a fresh, disposable PostgreSQL 16 container, seeds synthetic A/B rows using the existing fixture definitions, and holds a real uncommitted transaction open in one psql process while another independent connection calls the restore function. No hosted database credentials or network connection to Supabase are used.
Cases: concurrent ordinary ledger edit versus restore, concurrent ordinary strategy edit versus restore, competing restores from the same snapshot, and ordinary ledger optimistic revision comparison. During uncommitted operations the second session must receive 55P03 (lock not available). Once the first transaction commits, replaying the stale snapshot must receive 40001; no blind retry. The test compares complete owner snapshots and checks B remains unchanged, then tests a freshly reviewed restore.
The current prototype locks both tables, so contention can affect different users. The fixture does not prove per-owner concurrency or existing browser strategy saves have revision guards. Production integration requires full server schema review, authoritative validation including forecast metadata, real TEST auth/RLS, safe handling of conflicts and uncertain outcomes, and separately approved migration/restore. No changes to existing accounts, Supabase, TEST Pages, or prior Draft PRs.
