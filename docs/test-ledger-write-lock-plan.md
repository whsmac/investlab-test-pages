# INVESTLAB TEST — 원장 쓰기 권한 잠금 설계 / 적용 보류

**상태: 보안 검토 문서. DB에 적용하지 않았음.**

## 발견된 위험
기존 v2 초안은 authenticated 사용자에게 원장 테이블 INSERT/UPDATE/DELETE를 직접 허용한다. 따라서 원자적 RPC의 잔고 확인, 중복 방지, 계좌 잠금 규칙을 우회할 수 있다. RLS는 행의 소유권만 제한하며, 거래의 경제적 정합성을 보장하지 않는다.

## 수정해야 할 최종 권한 모델
- 계좌: 소유 사용자만 조회. 생성·이름 변경은 검증된 API 경로에서만 수행
- 원장 이벤트/legs: 소유 사용자 SELECT만 허용. INSERT/UPDATE/DELETE는 브라우저 역할에서 전부 REVOKE
- 원장 쓰기: 검증된 RPC만 허용. RPC 실행권한은 PUBLIC/anon에서 REVOKE, authenticated에 명시적 GRANT
- SECURITY DEFINER: 최소 권한의 전용 소유자, 고정 search_path, 함수 내 auth.uid() 확인, 계좌 소유권 및 원자성 검증
- 실제 원장 확정 후 변경·삭제 불허. 오류 정정은 역거래/정정 이벤트
- 사용자별 거래원장과 시나리오는 별도 정책 적용

## 안전성 추가 요구
1. 기존 v0 RPC는 `SECURITY DEFINER` 권한/소유자 감사 전 설치 금지.
2. DB 역할이 직접 원장에 쓰는 경로(다른 RPC, 트리거, 권한 상속 포함)를 모두 조사해야 함.
3. PostgreSQL 함수는 기본적으로 PUBLIC EXECUTE 권한이 부여될 수 있으므로 **CREATE FUNCTION과 REVOKE를 같은 트랜잭션**으로 처리해야 함.
4. 원장 테이블의 인증 사용자 직접 쓰기를 차단한 뒤에야 원자적 함수의 잠금 규칙이 유효함.
5. API 수준 테스트는 TEST 사용자 A, B, 비로그인 상태 각각에서 수행. SQL Editor의 관리자 실행은 RLS 증명이 아님.
6. 계좌와 이벤트의 user_id 변경을 명시적으로 금지하고, 중복 요청 시 payload 완전 비교, 수수료/환율/정정 처리 보완.
7. TEST 프로젝트 ID 확인, 롤백 계획, 기존 테이블 이름 중복 점검이 선행되어야 함.

## 이번에 작성한 읽기 전용 점검
`sql/test-ledger-security-audit-READONLY.sql`은 제안된 테이블 5개가 있는지, RLS 및 권한이 어떤 상태인지, 동일 이름 RPC가 존재하는지 확인한다. **테이블이 아직 없어도 실행 가능**하도록 작성했다. 결과는 테이블별 5행과 RPC 조회 결과로 나뉜다.
